# 「今回はちゃんと設計してから渡そう」を、毎回飛ばしていた話

副業で AI に bot のコードを書かせていて、ある機能を3回作り直したことがあります。

1回目は「想定してない挙動が出た」で作り直しました。2回目は「別の仕様欠陥が出た」で作り直しました。3回目に入るとき、ようやく気付いたんですが、私は毎回「仕様の何かが足りない」まま実装に入らせていて、AI 側は仕様の穴を良かれと思って埋めながら作っていただけでした。1回目も、2回目も、正しいコードが返ってきていました。私の仕様が穴だらけだっただけで。

毎回、作り直しに入る前に「次はもっと丁寧に設計してから渡そう」と思っていました。それを3週間、毎回思って、毎回飛ばしていました。

副業で AI を使い始めて気付いたことを、いったん書き残しておきます。

## 「急いでるから今回だけ」が毎回だった

最初の頃、私は全部1ターンで投げていました。「この機能作って」「このバグ直して」「このリファクタやって」。タスク内容と実装の詳細を一気に書いて、AI に渡す。

コードは出てきます。テストも通ります。コミットします。

問題は、**設計の判断と実装が同時に走る**ことでした。仕様に曖昧な部分があると、AI 側は「たぶんこうだろう」で自分で埋めながら進めます。返ってきたコードは動いているので、そのまま採用します。テストが通っているのに、仕様がずれている、という状態に気付くのは、だいたい1週間後です。「この挙動、頼んだ覚えがないんだけど」。そのとき初めて、AI が穴を埋めていたことに気付きます。

> コードが正しいのに、仕様がずれていた。

コンパイルが通って動いているものを「これは想定外だった」と判断するまで、1週間かかっていました。

「次はもっと丁寧に設計してから」。毎回こう思っていました。

毎回、次が来るときには飛ばしていました。「急いでるから今回だけ」を、3週間続けていました。

「急いでるから今回だけ」が毎回なら、「今回だけ」が普通になっているだけです。気付いたのは3回目の作り直しに入ろうとした朝でした。コーヒーを入れて、ログを開いて、「あれ、またここか」と思った瞬間でした。

途中から、Slack より先に bot のログを開く朝が続いていました。意味があったかは分かりません。

## 自分が設計を渡さなかったから、AIが埋めるしかなかった

3回目の作り直しに入る前に、少し立ち止まりました。

1回目の実装で出た「想定してない挙動」と、2回目の実装で出た「仕様欠陥」を並べてみたら、両方とも私が書き忘れていた部分を AI が判断して埋めたものでした。AI は正しく動いていました。私が曖昧なまま投げたから、AI が埋めるしかなかっただけです。

**AIに投げやすいから、設計する前に投げてしまっていた。**

それだけでした。1分書けばコードが返ってくる便利さが、「設計してから渡す」を毎回省略させていました。

「設計と実装を、構造的に分離しないと無理だな」と思ったのがそのときです。思うだけなら前からしていたので、何か物理的に間に挟まないと、また飛ばすと思いました。

## 同じ AI を、別の役で2回呼ぶことにした

なので、エージェントを2役に分けました。

「考える役」と「書く役」です。考える役は仕様だけ作る。実装はしない。書く役は仕様を受け取って、その通りに実装する。設計の判断はしない。

Planner-Coder と呼んでいますが、実態は同じモデルを別の役で2回呼ぶだけです。考える役には Copilot CLI の GPT-5.4 を使って、書く役は Claude Code の Sonnet。得意な領域が違うので自然と分かれますが、「1ターンで全部やらせるのをやめた」だけです。

これで物理的に、考える役が仕様を出すまで書く役は動きません。私が「急いでるから今回だけ飛ばそう」と思っても、考える役を呼ばないと書く役に渡せない。この「飛ばしにくい状態を作る」が目的でした。

## 毎回判断したくないから、雑な表を置いた

問題は、考える役を呼ぶべきかどうかを毎回判断するのが面倒だったことです。typo 修正まで考える役に通すのは無駄で、新機能の設計を書く役に直渡しするとまた3回作り直しになります。

最初は毎回その場で考えていたんですが、1日に5回も10回もタスクが流れてくると、毎回5分悩んでいるだけで時間が溶けます。

> 毎回判断したくない、というだけの理由でスコア表を置きました。

最初は2項目だけでした。「指示が長いか」「設計キーワードが入っているか」だけ。これだと typo まで考える役に通したので、「単純キーワードがあれば減点」を足しました。それだと既存パターンの横展開が見抜けないので「既存パターンなら減点」を足しました。何回か踏むたびに1項目ずつ足していって、いまの形になりました。

| シグナル | 加点 |
|---|---|
| 指示の長さ200字以上 | +2 |
| 設計キーワード（新機能 / 設計変更 / 移行） | +3 |
| 抽象度（「〜したい」だけで手段不明） | +3 |
| 不変条件に触れる可能性 | +3 |
| 単純キーワード（typo / 修正して / 設定変更） | -2 |
| 既存パターンの横展開 | -2 |

合計6点以上なら考える役を通す、5点以下なら書く役に直渡し。

これも完成した設計表に見えますが、整理したかったわけじゃなくて、毎回その場で迷うのが嫌だっただけです。踏むたびに1行足していったら、いまの形になっていました。

スコアを計算するだけなので5秒で終わります。毎回「どっちに渡すべきか」で5分悩んでいた頃と比べると、3回目の作り直しに入る前に止まれることが増えた、くらいの変化です。

## 考える役の設計に、別の AI にケチをつけてもらうことにした

考える役が仕様を出したあと、すぐ書く役に渡さないようにしました。間に1つ挟みます。

同じ Copilot GPT-5.4 に「この設計の盲点を挙げて」と頼みます。Bear と呼んでいますが、「別の AI にケチをつけてもらう」だけです。盲点が3つ以上あれば設計やり直し、2つ以下なら警告付きで実装に進む、というルールにしています。

最初は考える役の出力を Bear にそのまま渡していたんですが、Bear が考える役の設計を読んでから批判するので、同じ枠の中で改善案が出るだけでした。**最初の設計が基準になって、Bear がその基準の中を批判するだけ**になっていました。正しい批判なんですが、設計そのものを見直す視点が出てきませんでした。

なので、重い案件のときだけ、Bear に考える役の出力を見せないで元の問題だけ渡して、独立に再設計させる形にしました。2つの設計の差分を見ます。差分が大きければ最初の設計に引きずられていた証拠、小さければ本当に堅い設計、という判断にしています。

毎回これをやるとコストがかかるので、軽い案件では普通に Bear に出力を見せて批判させるだけです。スコア8以上の重い案件のときだけ切り替えます。

## 「これくらいなら」でケチったとき

設計を2役に分けてからも、1回だけ「これくらいなら」で考える役を飛ばしました。スコアが7点のタスクで、「7点ならギリギリ飛ばしてもいいだろ」と思いました。

1回目の実装が完了しました。テストが通りました。レビューしたら「書き込み禁止の場所に接続されている」という仕様違反が出ました。再実装。

2回目が完了しました。書き込み先は直りましたが、「型が別のモジュールの期待する型と合っていない」という別の欠陥が出ました。再実装。

怖かったのは、2回ともテストが通っていたことでした。コードは間違っていませんでした。仕様の定義が曖昧なまま実装に入ったので、AI が「たぶんこうだろう」で埋めた部分が、後から別のモジュールの前提と噛み合わないだけでした。「テストが通った = 正しい」じゃなくて、「私が書き忘れた仕様を AI が自分で判断して埋めた結果として通った」というだけで。

3回目に入るとき、またです。**設計を決めないまま実装を繰り返しているだけで、何回直しても根本は変わらない。**

考える役を最初に通していれば、仕様書に「書き込み先の制約」と「型の定義」が書かれていて、書く役はそれを実装するだけになっていました。3回のループが1回で終わっていたはずです。

「設計をケチる」は結果として安くなかった、というのは頭では分かっていました。ただ毎回飛ばしていました。急いでいるときほど飛ばしていました。

## 朝、3回目の作り直しに入る前に止まれることが増えた

考える役と書く役を分けてから、書く役の1回目の実装がそのまま動くケースが増えました。

地味な変化ですが、朝「またここか」と思う頻度が前より減っています。以前は2回目の作り直しに入るのが普通でした。今は、仕様の段階で議論が終わっているので、書く役に渡した時点でほぼ答えが出ている状態になっています。

全部直ったわけではありません。重い案件では、考える役と Bear と私の3者でだいぶ長く議論することがあります。でも「設計が足りなかったので実装からやり直し」は、前ほど来なくなりました。

## 同じ症状を聞きます

最近、似た話を聞くことが増えました。

「AI に頼んだコードが1週間後に仕様違反で出戻る」
「同じ機能を何回も作り直してる気がする」
「『次はもっと丁寧に設計してから』を毎回言っている」

私もずっとそうでした。AI にすぐ投げられる便利さが、設計を飛ばす方向に引っ張っていきます。1ターンで全部やってくれる見た目があるから、設計と実装を一緒にやらせてしまう。AI が悪いというより、**AIにすぐ投げられるから、設計前に投げてしまった**だけです。

## 「毎回飛ばす自分を止めるため」に2回呼んでいる

スコア表と、考える役 / 書く役 / Bear の役割分担、1ページのメモに置いてあります。

立派なドキュメントを作りたかったわけじゃなくて、毎回「今回は飛ばしてもいいか」と迷うのが嫌だっただけです。飛ばしにくい構造を先に置けば、毎回飛ばす理由を探さなくて済みます。

中身を整えようとすると、逆に更新しなくなる気がするので、雑なまま運用しています。もし参考にしたい人がいれば、有料記事として出してもいいですが、整えるほどの体系にはなっていません。

これが最終解だとは思っていません。たぶんまた「これくらいなら飛ばしていいだろ」が来ます。急いでいるときほど。今のところ言えるのは、飛ばしにくい状態を先に作っておけば、飛ばす回数が少し減る、というくらいです。
