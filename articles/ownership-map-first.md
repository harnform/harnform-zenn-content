# systemctl active なのに、12時間出力が止まっていた話

朝、いつものようにパイプラインの出力ファイルを開いたら、最終更新が12時間前で止まっていました。

`systemctl status` は active のまま。`journalctl` を見ても例外は出ていない。データソース側も普通に生きている。なのに、出力だけ止まっている。

最初はタイマーの定義を疑いました。依存関係、リトライ回数、ログローテートで stdout が消えたんじゃないか。順番に潰していったんですが、結局どれも壊れていません。

何が悪いのか分からないまま、「とりあえず再起動」を3回しました。朝に再起動して、夜にまた止まる。同じ症状が場所を変えて出る。

3回目までは「たまたま今日は機嫌悪いんだろ」くらいに思っていました。1週間続いてようやく「あれ、これ運じゃないな」となりました。

副業で複数の自動売買 bot を回しています。3ヶ月運用していて起きたことを、いったん書き残しておきます。

## 再起動で逃げていた

最初の月、私の自動化は本当によく止まりました。3週間で「再起動」を10回くらいしたと思います。各 bot を再起動して、しばらく見て、動いてれば次の作業に戻る。

何で落ちたかを毎回特定できていなかったので、また同じ場所で同じ落ち方をしていただけでした。「再起動したら直るだろ」で済ませていたので、根本では何も変わっていません。最初は真面目に原因を追っていたんですが、途中から普通に再起動で逃げていました。

朝、ログを開く前にちょっと時間置くようになっていました。

「今日は止まっていないといいな」という感じで、少しためらってから開く。自分が作ったはずのパイプラインで、止まるたびに「今日はどこだろう」と確認するのが、普通にしんどくなってきた時期でした。

止まったときに本当に困ったのは、直し方が分からないというより、「これは誰が気付いて、誰が直す話なのか」がどこにも決まっていなかったことでした。自分しか確認する人間がいないのに、確認するための仕組みを作っていなかった。止まるたびに自分が気付いて、自分で何とかして、疲れたら再起動で逃げていた。そのループでした。

## 「例外は出てない」って、本当に確認できていたか

ある日、3本の bot を並行で動かしていて、また1本止まっていました。`journalctl` の出力を見て、いつものとおり「例外は出てない」と書こうとしたところで、手が止まりました。

> いや、なんで毎回「例外は出てない」って書いてるんだろう。

ログをよく見たら、別の処理のコンテキストが上書きしていて、本来そこに出ているはずのスキップ理由が、別の処理の値で埋められていました。コードの中で複数の処理が同じデータ辞書を共有していて、後発の処理が前のログ値を踏みつぶしていたんです。

普通にログ壊れてました。

当時は気付いていなかったんですが、今見るとたぶんこの辺から崩れていました。monitoring しているつもりで、実際には埋められた値を毎日眺めていただけです。ログを見ているのに、見ているログが壊れているの、結構怖かったです。

怖さの中身を少し整理すると、「間違えた」のではなく「正しく確認していると思っていたのに、確認できていなかった」という種類の怖さでした。例外がないのは、例外を見るためのログ自体が別の値で上書きされていたから。「異常なし」という正しそうな出力が出ていたので、3週間気付けなかった。

エラーログが赤字で出ていれば気付ける。でも正常に見える出力が返ってきていると、疑う理由がありません。確認したつもりになれてしまう。

これに気付いてから、症状が消えても再起動で済ませない、と決めました。

## 「これ、誰が直すんだっけ」で5分止まる

もう一つ困っていたのが、止まったときに自分が動くべきか、調査を専門の担当に投げるべきか、毎回決めかねていたことです。

ログを1〜2コマンド見れば原因が分かるなら、自分で直したほうが速い。コードを複数ファイル追って原因特定するなら、調査用の担当に委譲したほうがいい。これを毎回その場で考えていると、5分くらい悩みます。1日3回止まると、それだけで15分が消えます。

「これ、誰が見るんだっけ」で5分止まる。1日に何度かそれをやると、昼休みが終わっています。

ある日、これを文章で固定しました。「ログ調査が2コマンド以上かかりそう / コードを読んで原因特定が必要 / 複数ファイルを追う必要がある」のいずれかなら委譲、それ以外は自分で直す。毎回口の中で考えていたことを、ファイルに書いただけです。

最初は真面目に毎回判断していたんですが、途中から「考えるのが面倒」が勝っていました。判断をやめたかったというより、毎回同じことを判断したくなかっただけです。

これでだいぶ静かになりました。

## state ファイルは「稼働中」、実際には inactive

もう一つよくハマったのが、書いてある状態と実態がズレるパターンでした。

各 bot に「いまどう動いているか」を書いた状態ファイルを置いていました。先頭に `last_updated:` を入れて、変更があったら更新する運用です。

これを信じてセッション再開すると、たまに事故ります。状態ファイルは「稼働中」と書いてあるのに、実際に確認したら inactive、というケースが何回かありました。私が更新を怠ったのか、自動更新の処理が落ちたのか、その時点では分かりません。

「稼働中と書いてあったのに止まってた」という事故は、見た目が正常なぶん発見が遅れます。エラーが出ていれば気付ける。状態ファイルが更新されているように見えているとき、何かが止まっているかもしれないとは思いません。

なので、ライブ稼働している bot を触る前に、必ず実際のランタイムを確認することにしました。書いてある状態と実態が違ったら、実態のほうが正しい。書いてあるほうを直す。

当たり前に聞こえますが、「書いてあるから大丈夫」で2回くらい事故ったあとにようやくそうしました。そのあたり、ちゃんと直して、しばらくしてから同じことをやっていました。

## `.tables` を叩いたら、思っていたより多かった

ここまでの3つを並べてみると、タイマーの問題ではなく、「どこに書いて、誰が読んで、誰が直すか」が決まっていなかっただけでした。

なので、自分が何箇所に書き込んでいるかを書き出しました。sqlite なら `.tables`、ファイルなら `find` で雑に出すだけ。

`.tables` を叩いたら、思っていたよりかなり多くて、そこで少し嫌になりました。こんなに書込先があるのか、という感じです。

書込先を全部並べて、「これは誰が書く」「これは誰が読む」「これ壊れたら誰呼ぶんだっけ」を1個ずつ書きました。最後の「誰が直す」だけでも先に決めておくと、止まるたびに5分悩むのがなくなって、地味に楽でした。

owner がいない書込先が複数あった、というだけの話でした。自分だけで回しているつもりでも、「これが壊れたとき誰が気付くか」の答えが空欄になっている箇所は、思ったより多かったです。整理したかったというより、止まるたびに「誰が何とかするんだっけ」で固まるのが嫌だっただけです。

## 「将来の自分は普通に bypass する」

書込先を整理したあと、もう一段下のガードを入れました。

最初はアプリ側だけでチェックしていました。「このストリームは観測専用で、収益データには書けない」というルールを関数の中に書く形です。

でも将来の自分って、普通に bypass するんです。半年後に「ちょっとだけ」と例外を作る。直接 SQL を叩いたら、アプリ側を通らずに書ける。

なので、DB 側でも弾くようにしました。

```sql
stream TEXT NOT NULL CHECK (stream IN ('articles', 'skills', 'bounty'))
```

変な書き込みしたら、DB 側で怒られます。アプリ側も、想定外のストリーム名が来たら関数の入口で怒るようにして、両方の入口で同じことを言わせています。

二段にしたのは、将来の自分を信用できなかったからです。アプリ側だけだと、直接 SQL を叩いた瞬間に抜けられる。DB 側だけだと、半年後の自分が「ちょっとだけ」と制約を緩めます。両方そろっていないと、自分が壊しに来る。将来の自分は、わりと信用ならないんです。

最初からこういう設計にすればよかったとは思います。ただ「最初からちゃんと設計しよう」と毎回思って、毎回飛ばして、壊れてから直すというのを何回かやって、ようやくここに落ち着きました。

## ついでに失敗ノートも分けた

書く場所を整理したついでに、失敗ノートの書き方も変えました。

私は失敗を JSONL に1件1行ずつ書き溜めています。最初はスコープなしで全部混ぜて書いていて、新しいタスクを始めるときに関係ない失敗まで毎回読み返すことになって、だんだん読み返さなくなっていました。

各行に「これは特定 bot 固有の失敗か / 全 bot 横断で再発するコーディング失敗か」を付けるようにしただけです。それで、その bot を触るときに関係する失敗だけが目に入るようになりました。

踏み出せなくて、しばらくスコープなしで全部混ぜたまま置いていました。100件超えたあたりから、これが分かれていないと読み返さなくなる、というのが体感で分かってきました。分けたのはそのあとです。「整理したかった」というより、「読み返さなくなるのが嫌だった」ほうが正確です。

JSONL は grep できるから選びました、と言えば選定理由になりますが、実際は Markdown だと罫線を整え始めて時間が溶けるし、git log は残っているけど書く瞬間には思い出せないし、テキスト1行追記が一番続きました。続くから使っているだけです。

## 最近、似た話を聞きます

最近、似た症状の話を聞くことが少しずつ増えてきました。

「`systemctl status` は active なのに、出力が止まっている」
「ログには異常がないのに、何かが進んでいない」
「再起動すると一旦動くけど、また同じ場所で止まる」

私もそう思って、3週間ぶん、再起動と設定見直しで時間を使いました。たいていタイマーや定義の問題だと思って探しに行くんですが、私の場合は、「これが落ちたとき、誰が気付いて、誰が直すか」がどこにも書かれていなかっただけ、ということが多かったです。

止まるのが問題ではなく、止まった場所に担当が書かれていなかった。これに気付くまで、なぜか「タイマーが悪いんじゃないか」「依存関係がおかしいんじゃないか」を先に調べに行っていました。自分が確認先を決めていなかっただけ、というのが一番見えにくかったです。

## 自分用のメモにしている

このあたりの確認を、いつ・どこを見るか、で書き出して自分用のメモにしています。書く場所、読む場所、直す場所が日付ごとにズレていないかを見るための表です。

最初は2行しか書いていなかったんですが、止まるたびに1行足して、いまの形になりました。整理したかったというより、毎回「誰が直すんだっけ」で固まりたくなかっただけです。

まだ整理中ですが、似たところで詰まっている人がいたら、近いうちに有料記事として出すつもりです。中身は、書込先の整理、担当の決め方、状態ファイルの使い方あたりです。

これが最終解だとは、まだ思っていません。たぶん、また別の場所で止まります。止まったとき「誰が直すんだっけ」で固まる回数が、少し減っただけです。
