# AIに作業を任せたら、毎回説明し直す仕事が増えた話

副業で AI に bot を作らせ始めたころ、正直かなり楽になると思っていました。

夜に依頼を投げて、朝起きたら何か進んでいる。昼休みに少し確認して、夜にまた次を投げる。そういうイメージを持っていました。

実際にやってみたら、昼休みに進捗を見て、夜にエラーを拾って、週末に引き継ぎ資料を書いていました。あれ、これ楽になってるか？ と思ったのが、これを書いているきっかけです。

ある日、自分が毎日何をやっているか書き出してみました。

- 指示書を書く（毎朝）
- 進捗を聞く（昼休み）
- エラーを引き取って自分で直す（夜）
- モデル間で引き継ぎ資料を作る（週末）
- 過去の失敗を思い出して同じミスを止める（毎日）

ここまで書いて、少し嫌な気持ちになりました。これ、AI 活用というより、普通に管理職の仕事では？

副業のために始めたはずなのに、本業が終わったあとに、もう一つ小さい職場を見ている感じになっていました。AI が仕事を奪うと言われていましたが、私の周りで実際に起きたのは、AI が増えたぶんだけ、人間側に「AI を管理する仕事」が増えていたことでした。

prompt を磨くのを諦めて、代わりに AI 用の社内規定を書く方向に切り替えました。少なくとも私の環境では、こちらのほうがかなり効きました。同じところで詰まっている人もいるかもしれないので、いったん今の状態を書き残しておきます。

## 「もっと強い prompt があるはず」と思っていた

最初の3週間、私はとにかく「使えるプロンプト」を集めていました。GitHub の awesome-prompts、X で流れてきたテンプレ、公式クックブックの抜粋。120本のコピペ用テキストが手元に溜まりました。

ある時期、自分の中で「強い prompt ランキング」みたいなものを作っていました。「設計フェーズ最強テンプレ」「リファクタ最強テンプレ」「テスト書かせ最強テンプレ」。フォルダに「神 prompt 集」みたいな名前を付けていました。今見るとかなり恥ずかしいですが、そのときは本気で解決策だと思っていました。

途中からは、prompt を整理するための prompt まで作っていました。今思うと、完全に本末転倒です。コードを書くより prompt を品評する時間のほうが長くて、「もっと強い prompt があるはず」と思って探し続けていた、と言ったほうが正確かもしれません。

そして、こういう瞬間を何度か通過しました。

- 朝起きたら、夜に投げた実装担当が commit 直前で止まっていた。コンテキストを食い切って、最後のレビュー工程だけ落として帰宅していた
- 同じ仕様で retry した結果、3回とも同じ失敗で戻ってきた
- 設計担当にだけ長文を書かせて、実装担当には1行で渡してしまい、解釈の食い違いで2回作り直し
- 昼休みにスマホで進捗を見たら、設計担当だけ長文を吐き出して止まっていた

途中から、Slack より先に作業ログを開く朝が増えていました。意味があったかは分かりません。

最初は「もう一回投げたら通るかも」と思って retry していました。AI はたまにそれで通ります。ただ、同じ失敗を3回返されたときに、これは運ではなく、仕組みの問題だと分かりました。

prompt は1ターンの指示でしかないんです。1ターン目に刺さっても、3ターン目には「提案できません」と返してきます。別のモデルに切り替えると引き継ぎが下手で、週をまたぐとコンテキストが切れます。

ターンごと・モデルごと・週ごとに、私が手作業でつなぎ直していた。これが棚卸しで出てきた「管理職っぽい仕事」の正体でした。

3週間目あたりで、prompt をいくら増やしても、自分のさばく量しか増えないんだと気付きました。

## 「設計してから渡そう」を、3週間ずっと飛ばしていた

方針を変えるまで、私は毎回「次こそちゃんと設計してから渡そう」と思っていました。毎回飛ばしていました。

AI にすぐ投げられる環境があると、設計する前に投げてしまうんです。待ち時間がないので、「とりあえず試してみよう」のコストがゼロに見える。設計をする前に依頼を投げて、出てきたものを見てから考える、というサイクルになっていました。

仕様を渡さなかったので、AI のほうで仕様を埋めるしかなかった。埋められた仕様が意図と違って、作り直しが発生する。作り直しの前に設計してから渡そうと思うんですが、次もまた飛ばす。

これを3週間繰り返しました。毎回「今回だけ」と例外を作っていた、と言ったほうが正確かもしれません。

## prompt ではなく、毎回口で説明していたことをファイルにした

なので方針を変えました。やったことを一言で言うと、毎回自分が口で説明していたことを、そのままファイルに書いただけです。

具体的にはこういうことを書きました。

- 「この作業は先に設計が必要、これは直行」というタスクの振り分け方
- 「この担当は起動前にこのファイルを必ず読む」という朝会の手順
- 「終わったら親にこの書式で報告する」という引き継ぎ書のテンプレ
- 「前回このbotではここで壊れた」という過去の失敗の記録

毎回口で言っていたから、忘れたり、抜けたり、担当によって違う説明になっていました。それを文章で固定して、起動時に必ず読ませるようにしました。

会社で言うと、新人を3ヶ月で戦力化するときの社内規定一式に近いと思います。役職と業務分掌、業務マニュアル、朝会フォーマット、引き継ぎ書、失敗事例集。最初は「AI チーム運営」みたいで面白がっていましたが、3週間くらいで普通に疲れました。もう戻れない感じはあります。

prompt を増やしても、「誰が、いつ、何を見るか」が決まっていないと、結局そこを自分が毎回つなぐことになります。自分の場合、足りなかったのは強い prompt ではなく、作業を回すための交通整理でした。

## 結局、効いたのは地味なルールだった

やったことは派手ではありません。強い prompt を見つけたわけでも、すごい自動化を組んだわけでもありません。毎回自分が口で説明していたことを、ファイルに書いただけです。

特に、この3つは効いた気がします。

### 振り分けスコア表

タスクが来たら、最初にスコアを計算します。指示の長さ、ファイル言及数、設計キーワード、抽象度、不変条件への接触、可逆性。それぞれに加点して、合計スコアで担当を決めます。スコア高ければ先に設計フェーズを挟む、低ければ実装担当に直行。

正直な表ですが、最初は2パターンだけでした。踏むたびに1行ずつ足して、いまの形になりました。判断したいというより、毎回5分悩むのが嫌だっただけです。

この表を作るまでは、ちょっとした typo 修正を設計フェーズに通して30分かけたり、逆に「新機能を設計したい」を実装担当に直渡しして仕様の食い違いで2回作り直したりしていました。毎回その場で考えていたのが間違いだったんだと思います。

スコア表を置いてから、振り分けミスによる作り直しは、記憶している限り最近は起きていません。「毎回考える担当」を、1人辞めさせた感じです。

### 朝会フォーマット（コンテキスト残量チェック）

実装担当のコンテキスト窓は有限で、アーキテクチャ・不変条件・既存知見の読み込みだけで半分近く食います。残った窓に実装＋テスト＋状態更新を全部詰めると、後半でコミット直前に力尽きる事故が起きていました。

朝起きてログを見ると、夜に投げた実装担当が「コンテキストが足りなくなったのでここで止まります」みたいな状態で帰ってきている。レビューも状態更新もコミットも、最後の一段だけ落として終わっている状態です。朝起きてログを見るのが、だんだん嫌になっていました。

なので、起動前にコンテキスト推定を必ず通すようにしました。

- 余裕（使用見込み50%未満）: そのまま投げる
- 分割必須（50%以上）: 担当を2つに分けて並行起動

お弁当箱の容量を計ってから、お弁当を詰める。やっていることはそれだけです。「気をつけて書いて」と書いても、AI のコンテキストにはダイエット効果がありません。

これだけで「最後だけ未完了で帰ってくる朝」が、ほぼなくなりました。

### 失敗事例集（再犯ノート）

JSONL ファイルを1つ用意しました。中身は運用中に出た失敗を1件1行で記録したもの。実装担当が起動前に必ずこれを読みに行きます。

- 特定 bot 固有の失敗: そのプロジェクトを触るときだけ参照
- 横断で再発するコーディング失敗（mock 過剰 / async await 忘れ / 循環 import 等）: 起動のたびに毎回参照

現時点で60件超。「再犯ノート」と呼んでいますが、要は「同じミスを2回しないためのメモ」です。保護観察官みたいで自分でも気が引ける名前ですが、効きます。

以前の私は、過去のミスを記憶で持ち歩いていました。実装担当が起動してきたら「前にこういうミスがあったから気をつけて」と毎回口頭で言っていた。これを文章で固定して、起動時の規定に組み込んだだけです。私が記憶を司る役を降りました。

正直、この辺はかなり泥臭いです。が、効きます。

## AI を使っていたつもりが、AI の世話をしていた

ディレクトリで書くとこういう形になりました。

```
~/<workspace>/
├── CLAUDE.md                    # 親プロセスの規定
├── .claude/rules/
│   ├── planner-coder-flow.md    # 振り分けスコア（中身は雑な加点表）
│   ├── subagent.md              # 朝会フォーマット
│   ├── parent-role.md           # retry / 呼び戻し / 誰に投げる
│   └── bear-calibration.md      # 採用するか捨てるかの閾値
├── <Bot-A>/                     # 部署1: 株系
├── <Bot-B>/                     # 部署2: 暗号資産系
└── <Bot-C>/                     # 部署3: FX系
```

「bear-calibration というかっこいい名前がついていますが、要は設計にケチをつけてもらう別の AI を呼ぶかどうかの判断基準です。別 AI にケチをつけてもらうだけ」。整えると仰々しく見えますが、実態はそんなものです。

親プロセスが指示を受け取って、設計担当と実装担当に分けて投げる。各 bot は部署に相当して、専用の環境・フック・状態を持ちます。失敗ログとレビュー履歴は親が一元管理。

整理してから振り返ると、見えてきたのはこういうことでした。AI に仕事を渡しているつもりで、実際には自分が仕事を小分けにして、説明して、見張って、最後に片付けていた。3ヶ月かけてやっていたのは、「AI に作業させること」ではなく、「自分が AI の世話をしないで済む仕組みを作ること」でした。

そういえば昼休みにスマホで進捗を見る癖が、自然になくなっていました。管理画面を監視している人みたいになっていたので、ここが減ったのは気持ちのうえで一番大きかったかもしれません。

## モデルを変えたとき、prompt 集は使い回せなかった

このやり方の意味が出たのは、モデルを切り替えたときでした。Sonnet から別モデルへ、軽量モデルから高性能モデルへ、Codex への分担。これらを全部入れ替えても、規定の側は1行も変わりませんでした。役職定義・振り分けスコア・朝会フォーマット・引き継ぎ書・失敗事例集は同じファイルのままで、新しいモデルがそのまま読み込んで仕事を始めます。

prompt 集はそうはいきません。あるモデル向けに調整したテンプレは別のモデルだと冗長すぎ、軽量系のモデルにはそもそも入りきらない。3週間かけて集めた120本の寿命は、モデル切替1回ぶんしかなかったと思います。

新しいモデルが来たら、人事異動みたいに役職にあてはめて、規定に従わせるだけ。プロンプトを書き直す手間は、ほぼ発生しませんでした。

## 「AI に任せてるのに、自分のほうが忙しい」

あとから気付いたのですが、似たことを言っている人が、少しずつ増えていました。

「AI を入れたのに、なぜか終業時間が遅くなった」
「AI に投げる前提を整える時間のほうが長い」
「同じ説明を3つのモデルにしている」

最初はやはり気のせいだと思っていました。自分の段取りが下手なだけかもしれない、と。でも、どうやらそうではなかったみたいです。AI が増えると、人間側には「AI を迷わせない仕事」が新しく発生する。私はそれを3週間ぶん、prompt を磨くことで解決しようとしていた、というだけの話でした。

それがしんどいなら、prompt を増やす前に、運用ルールを1枚だけ書いてみる価値はあると思います。少なくとも私の場合は、これで戻ってこられました。

## 明日から書き出せる4ファイル

prompt を磨くより先に、自分の AI 組織のための規定を1日で書いてみてください。最低この4枚で動き始めると思います。

- 親が何をして、子に何を委譲するかの分掌（1ファイル）
- タスクの振り分けスコア表（10行のテーブル、最初は2行でいい）
- 担当の朝会フォーマット（コンテキスト残量チェック / 過去失敗の参照）
- 失敗事例集（再犯ノートとして JSONL 1個）

このあたりの運用ルール、自分用にチェックリスト化しています。まだ整理中ですが、「AI に任せているはずなのに、自分が毎回さばいている」という人向けに、あとで有料記事として出すつもりです。中身は、振り分け、引き継ぎ、retry、戻し方、失敗ログの残し方あたりです。

これが最終解だとは、まだ思っていません。たぶん、また別の問題が出ます。でも少なくとも今は、prompt を増やすより、AI が迷わないための運用ルールを書くほうに、戻ってきています。
